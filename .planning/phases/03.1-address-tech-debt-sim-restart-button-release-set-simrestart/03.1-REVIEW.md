## Warnings

### WR-01: Manual-clock tests wait for the gap sleep with `BlockUntil(1)`, which the old engine's ticker can satisfy

**File:** `internal/supervisor/watch_test.go:372-373` (also `internal/supervisor/supervisor_test.go:629`)
**Issue:** The comment says "the old engine's ticker is gone with its done channel". That is not what
the engine does. `Run` closes `e.done` inside `stopped()` (`engine.go:599`), and the ticker is stopped
afterwards by `defer ticker.Stop()` (`engine.go:530`) when `Run` returns. `clock.Manual.BlockUntil`
counts tickers as well as sleepers (`internal/clock/manual.go:84-93`). In `TestSimRestartReleasesAHeldButton`
the test continues after `<-old.done`, reads `Status`, and calls `BlockUntil(1)`. If the old engine
goroutine is preempted between `close(e.done)` and `ticker.Stop()`, `BlockUntil(1)` returns on the old
ticker, `Advance(2*time.Second)` runs before `SimRestart` has armed its gap sleep, and the gap timer
is then created at the already-advanced time. `SimRestart` never wakes. The test then dies on the 5 s
"no line" / "SimRestart did not return" timeout. The window is a few microseconds and I could not
reproduce it in 300 `-race` runs, so this is a latent flake, not a current failure. The same
assumption is in `TestSetInTheShutdownWindowIsStopping`, where it is less harmful because the next step
closes `downReq`.
**Fix:** Do not rely on a waiter count that includes a ticker about to be stopped. Either wait for the
engine's `Run` to fully return before arming the wait, or block on the exact count including the
ticker:
```go
// Make the engine stop deterministic: Run has returned (ticker stopped) once stopEngine returned.
// Option A: wait until exactly the gap sleep is registered.
clk := s.clk.(*clock.Manual)
clk.BlockUntil(1)       // the old ticker may still be counted ...
// ... so add a helper that waits for len(waiters) == 1, or expose
// Manual.Waiters() and poll until it equals 1 before Advance.
```
Simplest: add `func (m *Manual) Waiters() int` and poll `for clk.Waiters() != 1 { runtime.Gosched() }`
(with a real-time deadline) before `Advance`. Fix the comment, which is factually wrong.

### WR-02: `TestSimRestartReleasesAHeldButton` leaks the SimRestart goroutine and the replacement engine on any early failure

**File:** `internal/supervisor/watch_test.go:390` (cleanup registered at the very end)
**Issue:** The test starts `SimRestart` in a goroutine that blocks on the Manual clock's gap sleep.
The cleanup that stops the engine `SimRestart` installs (`t.Cleanup(func() { s.stopEngine(cur) })`) is
registered only after every assertion has passed. Any `t.Fatal` before that (the release line, the
`old.done` timeout, the `Status` check, the `restarted` line) skips it. `watchSup`'s cleanup knows only the
first engine, so the goroutine stays blocked on the clock forever and the second engine's listener
and ticker leak. In `go test` this leaks into later tests of the package (the socket directory is removed,
the goroutine and engine keep running), which makes a first failure produce confusing follow-on failures.
**Fix:** Register the cleanup before the failure points and make it tolerant of the slot state, for
example start the goroutine and immediately `t.Cleanup` a function that cancels the restart (close
`s.downReq` via `s.shutdown()` or `s.downOnce.Do`) and stops whatever engine is current under `s.mu`:
```go
t.Cleanup(func() {
    s.downOnce.Do(func() { close(s.downReq) }) // aborts the gap sleep
    <-errc                                      // SimRestart has returned
    s.mu.Lock(); cur := s.slot; s.mu.Unlock()
    s.stopEngine(cur)
})
```

## Info

### IN-01: `Set` doc comment promises more than the F6 arm delivers

**File:** `internal/supervisor/supervisor.go:1185-1187` and `:1241-1247`
**Issue:** The comment says "Every failing Set leaves the record as it was." In the `actx.Err() != nil`
arm the code comment itself admits "The engine may still apply the queued change before it stops". So a
Set can answer `stopping`, the record is rolled back, yet the engine has applied the change and the
`env`/`fan` event has already reached `sil watch`. This is accepted behaviour (shutdown is terminal,
F6 in the concurrency review), but the function doc is about the record only and a reader will take it
to mean "nothing happened". Together with F7 (a gap Set during a shutdown answers success while the same
Set after the aborted sleep answers `stopping`) the contract during a shutdown is "no guarantee".
**Fix:** Add one sentence to the `Set` doc: "During a shutdown a failing Set may still have reached the
engine; the instance is going down and the record is not used again."

### IN-02: C++ test leaves its temp directory behind when the `alarm(20)` watchdog fires, and has unused pieces

**File:** `tests/cpp/test_txcap.cpp:17, 90, 148, 319`
**Issue:** (a) `Env`'s destructor (socket file, `rmdir`) never runs if `SIGALRM` kills the process, so a
hung hub leaves `/tmp/siltxXXXXXX/bus.sock` behind on every failed run. (b) `<fcntl.h>` is not used.
(c) The return value of `setsockopt(SO_SNDBUF)` in `stall()` is ignored; if it ever fails the loop just
runs far longer before failing with "still connected after 200000 calls", which hides the real cause.
**Fix:** Install a `SIGALRM` handler that `unlink`s/`rmdir`s the path (kept in a static buffer) before
`_exit(3)`, drop `<fcntl.h>`, and `check(::setsockopt(...) == 0, ...)`.

### IN-03: The pinned "known limit" test encodes behaviour that contradicts the stated criterion

**File:** `uitest/hold_test.go:340-373` (`TestUSRSimRestartWithoutReleaseSendsAnUp`)
**Issue:** The test pins a path where the page sends a `button.up` across a restart and shows a
`button_not_held` message, which ROADMAP success criterion 2 describes as a user-approved known limit
(2026-11-10). It is documented and intentional, so this is not a defect. The risk is maintenance: the
test is green precisely when the spec'd ideal is not met, and it uses `settle(300ms)` sleeps to assert
an absence. The doc comment already says how to flip it; consider also tagging it in the test name or
a `t.Log` so a future grep for "known limit" finds it.
**Fix:** No code change required; optionally add `t.Log("pins known limit A-03.1-09, see ROADMAP Phase 3.1 criterion 2")`.

### IN-04: README says the firmware sees the release "when it resyncs with the next simulator" for every stop cause

**File:** `README.md:73-76`
**Issue:** The new bullet lists `sil sim restart`, `sil down` and an engine failure together, then says
the firmware sees the release when it resyncs with the next simulator. After `sil down` the firmware is
killed and there is no next simulator, and after an engine failure there may be none either (the
instance holds the failure). The statement is only true for a restart.
**Fix:** Reword: "...and, after a simulator restart, the firmware sees the release when it resyncs
with the new simulator."
