# Phase 03.1 Plan 01: Engine releases held buttons on stop Summary

**A stopping simulator engine releases every held USR button itself (`button` v false, reason `engine_stopped`, then a final snapshot with all buttons released), so `sil watch`, `sil status` in a `--gap` and the page agree with the firmware across `sil sim restart` and `sil down`.**

## Performance

- **Duration:** 7 min (12:33Z to 12:40Z)
- **Tasks:** 3 (1 tracer, 1 TDD-style, 1 auto)
- **Files modified:** 7 (production: 2, tests: 4, docs: 1)

## Accomplishments

- `Engine.stopped()` walks `ButtonIDs` after the `firmware` false event, releases each held button with reason `engine_stopped`, clears `holdUntil`, then publishes the final snapshot. No bus frame is sent (the bus is closed); the next engine's hello in-snapshot already tells the firmware the buttons are released.
- Proven on the real firmware with USR3 (a 50..1000 ms click, so a 2 s hold triggers nothing in the firmware): stream order is firmware false, `usr3` false `engine_stopped`, `sim restarted`, firmware true; the gap status shows usr3 released; a late `sil press usr3 --up` answers `button_not_held`; a fresh press works.
- Every stop path pinned at engine, supervisor and e2e level (restart, shutdown, nothing held).
- The page across a restart is pinned both ways: with the release delivered no `button.up` is sent and the message line stays empty; without it, the known limit below.
- README gained the `engine_stopped` sentence and the "client re-reads the state after `sim restarted`" paragraph (A-03.1-04, doc only).

## Known limits

- **Missed-release path (user-approved 2026-11-10, not the spec).** A page that never receives the `engine_stopped` frame (its /ws subscription lagged and got a `lagged` marker, or its WebSocket closed during the restart) sends one best-effort `button.up` when the link is lost, because the Phase 3 link-loss behaviour (03-11) is kept. The restart gap answers `firmware_not_connected` or the next engine answers `button_not_held`, and the message line shows the refusal. No server or firmware state is wrong: the engine had already released the button. `TestUSRSimRestartWithoutReleaseSendsAnUp` pins this user-approved limit, not the spec. ROADMAP criterion 2 covers the path where the release is delivered. Fixing it means changing the page's link-loss release (a new UI-04 design decision); that change would flip the test and the ROADMAP note together.
- A `Set` accepted in a restart gap emits no `env`/`fan` event (A-03.1-04); documented in the README, classified in 03.1-02.
