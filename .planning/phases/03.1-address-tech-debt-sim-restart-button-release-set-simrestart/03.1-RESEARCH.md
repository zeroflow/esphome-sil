## Summary

**Item 1 (button release).** The cause is exactly as the audit says, and it is smaller than it looks. A new engine always starts with every button released and already tells the firmware so: its hello in-snapshot carries every button level, and the hub's binary sensor turns that into a release. What is missing is only the event stream and the stale status: the old engine's `stopped()` keeps `e.buttons` as it was, emits `firmware false` and nothing about the held button, and the supervisor publishes `sim restarted` only. So `sil watch` and the page keep a held state that no longer exists, and the page's later `button.up` is refused as `button_not_held` by the new engine. Recommended fix: make the **engine** release its own held buttons in `stopped()` (clear `buttons` and `holdUntil`, emit one `button` false event per held id with a new `Reason`, then publish), so events, final snapshot and `sil status` during a `--gap` all agree, and it works for every way an engine can stop. The page needs no change for the sim-restart case because the release event arrives on the old stream before `sim restarted` (the page already handles that via `onReleased`). One small optional page hardening (a snapshot that shows a button released also ends a hold the page had seen) covers `lagged` and reconnect resyncs.

**Item 2 (re-review).** I traced the four commits and the current code. The lock order (opMu, inMu, mu), the `engGap` window and the rollback logic hold up. Two real residuals were reproduced against a scratch copy of the repo: (a) IN-09 is confirmed (a `Set` between `downReq` closing and `stopping` being set returns `engine_failed`); (b) a **data race the previous reviews missed**: `Set` reads `len(s.fans)` without `inMu` (supervisor.go:1188) while another `Set`'s `rollback` assigns `s.fans` under `inMu` (supervisor.go:1202); `go test -race` flags it. Both are small, local fixes. A third observation (a `Set` accepted in a restart gap emits no `env`/`fan` event) is a design question for the planner, not a bug in the four commits. Structure: one review task that writes a REVIEW artifact and race tests first, then fix tasks only for confirmed findings.

**Item 3 (TX cap).** It can and should be an automated host-side C++ test. `sim_bus.cpp` compiles on the host against ~5 tiny stub headers (verified by prototype), a subclass can reach the protected `fd_`/`tx_`, `SO_SNDBUF` on the hub's fd can be shrunk so a non-reading peer back-pressures after a few KiB, and the drop fires after about 1200 `set_out` calls (65541 bytes pending, observed). The test then asserts: connection kept at or below the cap, dropped above it, WARN log text, `tx_` cleared, children notified, reconnect after the 100 ms backoff, and that the reconnect replays hello/chan/last-out/sync. It needs no Docker and no firmware build and runs in about a second under `make test-cpp`.

**Primary recommendation:** three independent plans: (1) engine `stopped()` releases held buttons + tests across engine, supervisor, e2e `across_sim_restart`, uitest; (2) review artifact + `-race` tests, then fixes for the confirmed `len(s.fans)` race and IN-09; (3) `tests/cpp/test_txcap.cpp` with stub headers wired into `make test-cpp` and `make test-cpp-image`.

### How the page and `sil watch` consume it

- `ui/web/js/app.js` forwards every `button` frame: `if (frame.v === true) onHeld(frame.id); else if (frame.v === false) onReleased(frame.id);`. `store.js` sets `state.buttons[frame.id] = frame.v` and on `sim` `restarted` returns `{resync: true}` (the page closes the socket and reconnects for a new snapshot).

## Recommended Design for Item 1

**Do:** release in `Engine.stopped()`, on the engine goroutine, before the final `publish()`.

```go
// Sketch (planner: adapt names, keep the order firmware false, then buttons).
func (e *Engine) stopped() {
	if e.connected {
		e.emit(events.Event{K: "firmware", V: false})
	}
	// A stopped engine holds nothing: its World goes away and the next engine starts released.
	// Say so, so streams and the final snapshot agree (CLI-03, UI-04).
	for _, id := range ButtonIDs {
		if e.buttons[id] {
			e.buttons[id] = false
			e.emit(events.Event{K: "button", ID: id, V: false, Reason: "engine_stopped"})
		}
	}
	e.holdUntil = map[string]time.Duration{}
	e.connected, e.synced, e.proto = false, false, 0
	e.btnAvail = map[string]bool{}
	e.publish()
	close(e.done)
}
```

Why the engine and not the supervisor:
1. During `sil sim restart --gap 3s` the status/watch snapshot comes from the stopped engine's final snapshot. A supervisor-only publish would fix the stream but leave `sil status` showing a held button for the whole gap. Engine-level fixes both.
2. It runs on the engine goroutine, so ordering against its own `firmware false` is deterministic and `emit` stamps seq/time through the existing path (`emit` uses `e.simNow`/clock, `inTick` false at this point).
3. It covers every stop path (restart, shutdown, failure), not just `SimRestart`.

Trade-offs and decisions for the planner:
- On `sil down` with a button held, the stream now gets one `button false` before the `stopped` line. That is truthful and harmless; if the planner prefers silence on shutdown, the alternative is the supervisor-side variant below.
- Reason string: the engine cannot tell restart from shutdown, so use a neutral `"engine_stopped"` (recommended) and document it next to `max_hold` in `events.go` and README. `[ASSUMED]` that no external consumer matches on reason values (project is 0.x, "sil watch event names and fields are internal while the project is 0.x (D-12)", events.go header).
- Supervisor-side alternative (not recommended): in `SimRestart`, after `s.stopEngine(old)` read `old.Snapshot().Buttons` and `s.broker.Publish(events.Event{T: s.clk.Now().Microseconds(), K: "button", ID: id, V: false, Reason: "sim_restart"})` before `sim restarted`. Leaves the gap-time status stale unless the final snapshot is also patched.
- Do **not** add a protocol message or a held-reset to the firmware: the existing hello replay already releases.
- Do **not** make buttons survive the restart (carry the held state into the new engine). That contradicts D-02 (fresh World) and A-02-01.

Optional page hardening (small, recommended as its own task): in `app.js`, after a `snapshot` frame, call `onReleased(id)` for every id whose `state.buttons[id] === false`. `onReleased` only acts when `seenHeld` is true, so a hold whose down is still in flight (`seenHeld=false`) is untouched. This covers the `lagged` and plain-reconnect resyncs where the release event was never seen. Test with the fake bench: hold, `b.Mutate(... st.Buttons[id]=false)`, `b.Emit(sim restarted)`, release the pointer, assert no `button.up` call and an empty message line.

### Concurrency invariants (re-derived, all hold)

1. Lock order `opMu -> inMu -> mu` is respected everywhere: `run()` takes `inMu` then `mu` (supervisor.go:273-281); `SimRestart` takes `opMu`, `mu` alone, later `inMu` then `mu`; `Set` takes `inMu`, then `currentEngine()` (`mu` briefly), then `mu` for `engGap`/`stopping`; `statusFrom`, `Status`, `isStopping` take `mu` only; `stopEngine`/`stopAll` take no `inMu`, so a `Set` blocked inside `Apply` is released when the engine is cancelled.
2. `engGap = true` happens under `mu` before `stopEngine(old)`; a `Set` can only get `ErrStopped` from the old engine after its cancel, and reads `engGap` afterwards, so it always sees the flag. Install and clear share one `mu` section (supervisor.go:844-856), and a `Set` that read `engGap` did so while holding `inMu`, which `SimRestart` also needs for `startEngine`, so a gap `Set` is always recorded before the new engine is seeded.
3. `Apply` with an uncancellable-by-caller context cannot hang a `Set`: the engine drains its inbox, `Send` is non-blocking with a bounded queue (`bus.Server.Send`, `sendQueue = 1024`), and `withDown` cancels on shutdown.
4. The `engDied` signal is not raised for an engine that `SimRestart` cancels (`up.Load() && ctx.Err() == nil` in `startEngine`).

### Residual findings (for the plan to confirm and fix)

**F1 (confirmed by `go test -race` on a scratch copy; not previously reported). Data race on `s.fans` header.**
`Set` computes `parseSet(r.Values, len(s.fans), s.library())` at supervisor.go:1188 without `inMu`, while `rollback` does `s.inputs, s.fans = prevIn, prevFans` at supervisor.go:1202 under `inMu`. The comment at the field says "Its length never changes after Serve, only its elements, under inMu" but `rollback` replaces the slice header. Reproduced with two goroutines calling `Set` on a supervisor whose engine is dead (no gap) so every call rolls back: `WARNING: DATA RACE ... Write ... Set.func1() supervisor.go:1202 ... Previous read ... Set() supervisor.go:1188`. Severity low (needs a dead engine), but it is a real detector failure that a future `-race` test of the failure path will hit.
Fix (pick one): roll back element-wise (`copy(s.fans, prevFans)`), or keep an immutable `nPorts int` set in `Serve` (e.g. `len(spec.Fans)`) and use it for `parseSet`/`knownKeys`.

**F2 (confirmed by test on a scratch copy; this is audit IN-09). `Set` racing a shutdown reports `engine_failed`.**
`shutdown()` closes `downReq` first, then waits for `opMu`; `s.stopping` is set only later in `stopAll`. When the gap sleep is aborted `endEngGap()` clears the flag while the slot still holds the stopped engine and `stopping` is still false. A `Set` in that window gets `ErrStopped`, reads `gap=false, stopping=false`, rolls back and returns `engine_failed: the simulator engine is not running; nothing was applied`. Reproduced: after `downOnce.Do(close(downReq))` and `SimRestart` returning `stopping`, `Set` returned `code="engine_failed"`.
Fix: in the `!gap` branch treat a requested shutdown like `stopping`: `if stopping || isDown(s.downReq) { rollback(); return control.SetResult{}, errStopping() }` (the Phase 2 review suggested the same). Test with the same recipe as the reproduction (manual clock, `GapS: 5`, close `downReq`, `Set`).

**F3 (design question, not a defect of the four commits). A `Set` accepted in the gap emits no events.**
`handleApply` is the only place that emits `env` and `fan` events, and it runs on the engine. A `Set` in the restart gap is recorded and seeds the new engine, but no `env`/`fan` event is ever published, so a `sil watch` consumer's state (snapshot + events) keeps the old value until the next change. The page is unaffected (it resyncs on `sim restarted`). Same class as item 1. Options: accept and document "`sim restarted` means re-read state" in README (cheapest), or have `SimRestart` publish `env`/`fan` events for values that differ between the old final snapshot and the new engine. Recommend documenting it and noting it as a known limit unless the planner wants to extend scope.

**F4 (minor, doc/robustness).** `Set`'s doc says "it never waits for a restart", but `inMu.Lock()` blocks while `SimRestart` holds `inMu` across `startEngine` (waits for `eng.Ready()`), and that lock is not cancellable by `ctx`. Bounded in practice (bus.Listen is local). Reword the comment; no code change needed.

**F5 (already known, keep out of scope unless trivially adjacent).** IN-08 (unreachable `default:` arm in `Set`) and the dead `s.stopping` branch in `SimRestart` (supervisor.go:846-851; `stopAll` runs only under `opMu`). If F2 is fixed, the `default:` rollback arm could be removed in the same edit or given a comment.

No deadlock, lost-update or missed-reset was found in `engGap`'s lifecycle.

## Item 3: 64 KiB TX-Cap Drop Test

### Code (verified)
- `components/sim_bus/sim_bus.h:46`: `static constexpr size_t kMaxTx = 65536;` with doc "The connection is dropped (and re-established with backoff) when this much is queued for a simulator that does not read, so a stalled peer can never grow or block the firmware loop."
- `sim_bus.cpp` `flush_()`: sends in a loop with `MSG_NOSIGNAL | MSG_DONTWAIT`, breaks on `EAGAIN`, then
  ```cpp
  if (this->fd_ >= 0 && this->tx_.size() > kMaxTx) {
    // kMaxTx is 65536 bytes: more than that queued means the simulator stopped reading.
    ESP_LOGW(TAG, "sim bus: %u bytes pending for a simulator that does not read; dropping the connection",
             static_cast<unsigned>(this->tx_.size()));
    this->close_();
  }
  ```
  `close_()` unregisters/closes the fd, clears `rx_`/`tx_`, sets `last_try_ = millis()`, picks the retry delay (welcome reached: `backoff_`; else `bump_backoff_()`), and calls `on_disconnected()` on every child. `loop()` reconnects when `millis() - last_try_ >= retry_delay_` (`kBackoffMin = 100`, `kBackoffMax = 2000`). `try_connect_()` replays hello, chan frames, `last_out_`, `last_px_`, sync.
- The requirement text: BUS-03 "The `sim_bus` hub component is non-blocking in the ESPHome loop, reconnects with backoff, and validates the socket path length at codegen". The TX cap is the 01-10 backstop truth: "The hub drops the connection and reconnects with backoff when its pending TX buffer exceeds 64 KiB, so a stalled simulator can never block or grow the firmware loop" (01-VERIFICATION.md must_have). Observable contract to test: no blocking, bounded queue, WARN line, connection dropped, reconnect with backoff, state replayed.

Recipe:
1. **Stub headers** under `tests/cpp/stubs/esphome/core/` (new dir, compiled with `-Itests/cpp/stubs`): `component.h` (a `Component` with virtual `setup/loop/dump_config/get_setup_priority`, `setup_priority::BUS`), `log.h` (`ESP_LOGW/I/E/CONFIG` writing to a test-visible sink so the WARN text can be asserted), `application.h` (`App.get_name().str()`), `hal.h` (`millis()`/`millis_64()` returning a test-controlled counter), `wake.h` (`wake_register_fd`/`wake_unregister_fd` no-ops). The signatures match ESPHome 2026.10.1 (`bool wake_register_fd(int fd); void wake_unregister_fd(int fd);` in `core/wake/wake_host.h`, `Component` virtuals in `core/component.h:152-169`, `setup_priority::BUS = 1000.0f`), checked in the pinned image.
2. **Test subclass** `struct TestBus : SimBus { using SimBus::fd_; using SimBus::tx_; using SimBus::retry_delay_; using SimBus::try_connect_; };` (members are `protected`).
3. **Make the stall fast and deterministic:** the test listens on a `mkdtemp` UDS path, `accept()`s, and never reads. After connect, `setsockopt(bus.fd_, SOL_SOCKET, SO_SNDBUF, 4096)` (kernel reports 8192 after doubling) so the kernel buffer takes only a few KiB; then call `set_out("port1.duty", 0.001f * ++i)` with changing values until `connected()` is false (cap the loop). Without the shrink the kernel default send buffer (hundreds of KiB) needs thousands more frames. The peer socket's receive buffer does not limit a UDS stream; the sender's `SO_SNDBUF` does.
4. **Assertions:** (a) while connected, `tx_.size() <= kMaxTx` after every `set_out` (observed max 65485); (b) the call that crosses the cap closes the connection (`connected()` false, `fd_ == -1`), `tx_` is empty, the WARN sink contains `bytes pending for a simulator that does not read; dropping the connection`, every registered child saw one `on_disconnected()`; (c) the loop never blocked (the whole test is bounded; add a wall-clock guard); (d) with the fake `millis()` advanced by less than `retry_delay_` (100 ms for a never-welcomed session) `loop()` does not reconnect, after it does; (e) the new connection's peer reads hello first and the stream contains the latest `last_out_` value for the channel and a final `sync` (state re-converges). Optionally a second case: a peer that *did* send `welcome` gets `retry_delay_ = backoff_` (reset).
5. **Exact-boundary case (optional):** the check is `>` so exactly 65536 bytes pending must not drop. Hard to hit exactly with real frames; skip or craft with `set_out_px` payload sizing.

## Common Pitfalls

### Pitfall 1: Testing SimRestart on a supervisor without firmware
**What goes wrong:** `SimRestart` waits for `BusConnected && Synced` up to `resyncBudget` (15 s) and returns `firmware_not_running` or `resync_timeout`. `buttonSupervisor`/`fanSupervisor`/`watchSup` have no firmware, and strict `SetButton` fails with `firmware_not_connected` anyway.
**How to avoid:** assert the button release at engine level (the harness has a fake firmware peer: `newButtonHarness`), and use real `SimRestart` only in the e2e or with the failing-start paths (`TestSimRestartKeepsAnExistingFailure` pattern).

### Pitfall 2: Using usr2 in the e2e hold-across-restart test
**What goes wrong:** `examples/rev33.yaml` gives USR2 `min_length: 1000ms`, `max_length: 10s` (long-press action: all fans 100 %); the replayed release on resync could fire it. USR1/USR3 use `min_length: 50ms`, `max_length: 1000ms`.
**How to avoid:** hold usr3 (or usr1) in the new e2e subtest; keep the USR2 long-press coverage in `TestWebAcceptance`.

### Pitfall 3: Assuming a page change is needed for UI-04
**What goes wrong:** over-scoping JS work. The page already releases its hold on a `button` false event, and the event arrives before `sim restarted` on the same ordered stream.
**How to avoid:** fix the server, add one uitest that proves the page behaviour, and only then decide on the snapshot hardening.

### Pitfall 4: Emitting from `stopped()` with an unsafe ordering
**What goes wrong:** `stopped()` publishes after `srv.Close()` and before `close(e.done)`. Anything that waits on `e.done` (Apply, SetButton, SnapshotSync) must not be needed to emit, and the emit must not block (broker `Publish` never blocks, verified). Keep `publish()` after the clearing so the final snapshot has released buttons.
**Warning signs:** tests that read `Snapshot()` right after `<-done` seeing a held button.

### Pitfall 5: `make test-pkg` with several packages
**What goes wrong:** `PKG` is one make variable inserted unquoted; `PKG=./internal/engine ./internal/supervisor` is parsed by make as a second goal ("Nothing to be done for 'internal/supervisor'", observed in this session).
**How to avoid:** quote it: `make test-pkg PKG='./internal/engine ./internal/supervisor' RUN=.`

### Pitfall 6: C++ test compiles but drifts from the firmware build
**What goes wrong:** stubs accept code that ESPHome would reject (or the reverse).
**How to avoid:** the test only certifies the hub logic; the firmware build in e2e remains the API gate. Keep the stubs minimal, mirror the 2026.10.1 signatures noted above, and run `make test-cpp-image` too.

### Pitfall 7: Hazard already known in this repo
`TestFirmwareBus` (e2e) fails if another process writes into the working tree during a run (audit, Phase 2 note). Do not run e2e while editing files.
