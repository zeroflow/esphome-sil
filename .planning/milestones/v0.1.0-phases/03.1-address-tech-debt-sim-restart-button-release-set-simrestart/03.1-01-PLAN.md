<objective>
Close audit tech-debt item 1 (cross-phase 01 resync x 02 buttons x 03 page): when the simulator engine stops while a USR button is held (a `sil sim restart`, `sil down` or an engine failure), the engine itself releases the button, announces it on the event stream with `reason` `engine_stopped`, and publishes a final snapshot with every button released. `sil watch`, `sil status` during a `--gap` and the page then agree with the firmware, which already sees the release when the next engine's hello in-snapshot replays released levels.

Purpose: CLI-03 (`sil watch` follows real changes), IO-03 (buttons), UI-04 (page press-and-hold). Today the old engine's `stopped()` keeps `e.buttons` as it was, so streams and the gap status keep a held button that no longer exists, and the page's resync sends a `button.up` that the new engine refuses as `button_not_held`.
Output: engine fix, event doc, engine/supervisor/e2e/uitest coverage of every stop path, README.
</objective>

## Planning notes (recorded decisions and assumptions)

- **Spec-less probe fallback: skipped.** The phase has no formally assigned requirement IDs to probe (visible skip). The plan references CLI-03, IO-03 and UI-04 because the work touches them.
- **A-03.1-01 (orchestrator default, research A2):** `sil down` with a held button also emits the release. The release lives in the engine's `stopped()`, so it covers every stop path (restart, shutdown, failure). Reversible: the stream format is internal while the project is 0.x (events.go header, D-12).
- **A-03.1-02 (orchestrator default, research A1):** the Reason value is `"engine_stopped"`. The only existing value is `"max_hold"` and the engine cannot tell a restart from a shutdown, so a neutral name fits. No external consumer is known to match on reason values (0.x).
- **A-03.1-03 (research A3, STATE A-02-01):** a sim restart releases a held button. The firmware measures the hold on its own clock and sees the release at the resync replay (existing `inSnapshot` behaviour, already pinned by `TestEngineSnapshotOrderAfterHello`). No firmware or protocol change. Buttons are never carried into the next engine (D-02 fresh World).
- **A-03.1-04 (research F3, orchestrator default):** a `Set` accepted in a restart gap emits no `env`/`fan` event. This is documented only, in README (Task 3): `sim restarted` means "re-read the state". No behaviour change. The finding itself is classified in 03.1-02's review.
- **Page snapshot hardening and the missed-release known limit (A-03.1-09, user-approved 2026-11-10).** The user accepted the missed-release path below as a known limit on 2026-11-10: keep the Phase 3 link-loss behaviour (03-11), no page change. Research's optional idea was "a snapshot showing a button released also ends a seen hold". It is not planned, because it would change nothing: every resync (`sim restarted`, `lagged`, a plain reconnect) goes through `lost()` -> `setLink("retrying")` -> `renderButtons` -> `release(cap)` before any new snapshot arrives (ui/web/js/app.js `lost`, ui/web/js/buttons.js `renderButtons`, `release`). By the time a snapshot could end the hold, the up has already been sent. The missed-release path itself can happen, though. It is a **known limit** of this phase. If the page never receives the `engine_stopped` release frame, the resync's `release(cap)` sends its best-effort `button.up`. That happens when the broker dropped the frame for a slow /ws subscriber and sent a `lagged` marker instead (internal/events/events.go), or when the WebSocket closed during the restart. The restart gap answers `firmware_not_connected` and the next engine answers `button_not_held`, and the page's message line shows that refusal (buttons.js `say`). No server or firmware state is wrong, because the engine has already released the button. ROADMAP success criterion 2 is narrowed to the path where the release is delivered; the narrowing is the user's decision of 2026-11-10 and the ROADMAP text carries the same label. Closing the limit would mean changing the page's link-loss release, which is UI-04's established best-effort behaviour. That would be a new page design decision, outside these tech-debt items. `TestUSRSimRestartWithoutReleaseSendsAnUp` (Task 3) pins the user-approved limit, not the spec, and the SUMMARY records it under known limits with that label. No change to ui/web/js.
- **Wave order (whole-tree gates in one working tree).** This plan is wave 1. 03.1-02 (wave 2) depends on it, and 03.1-03 (wave 3) depends on both. Every plan runs whole-tree gates (`make check`, which is `go test -race ./...` plus test-cpp; and e2e firmware builds). 03.1-02 commits red tests on purpose, and research Pitfall 7 says e2e fails while another process writes into the tree. So no plan's gate may overlap another plan's edits. This plan goes first because it is the phase's end-to-end tracer and it writes the README re-read paragraph that 03.1-02 cites for F3.
- **USR3, not USR2, in e2e (research Pitfall 2):** examples/rev33.yaml gives USR2 a 1000 ms..10 s long press; USR3 is a 50..1000 ms click, so a hold that spans a 2 s restart triggers nothing in the firmware.
- **Supervisor tests can call SimRestart (research Pitfall 1 resolved):** with no firmware (`fwRunning` and `restarting` false) the resync step fails on its first poll with `firmware_not_running`, as `TestSimRestartKeepsAnExistingFailure` (internal/supervisor/policy_test.go) shows. Use the Manual clock for the gap.
- **Wall-clock lint covers tests:** `internal/lint/wallclock_test.go` bans `time.Sleep`/`time.Now`/`time.After` everywhere outside internal/clock, including `_test.go` and tagged e2e/uitest files. Use `realClock`/`clock.NewReal()`, `sysClock`, `waitUntil`, `eventually`, `settle`, as the surrounding tests do.
